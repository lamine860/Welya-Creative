Chapitre 1 / 11 — Niveau débutant

Fondamentaux de Docker

Avant de foncer sur des commandes, il faut comprendre ce qu'est réellement un conteneur, en quoi il diffère d'une machine virtuelle, et comment les pièces du puzzle Docker s'assemblent. Ce chapitre pose les bases indispensables pour tout le reste de la formation.

1.1 — Le problème que Docker résout

Avant les conteneurs, le cycle de vie classique d'une application ressemblait à ça : "ça marche sur ma machine, mais pas en prod". La cause : des différences d'environnement — version de PHP, extensions installées, variables système, permissions fichiers, version de Node... Docker répond à ce problème en empaquetant une application avec toutes ses dépendances dans une unité portable et reproductible : l'image.

Analogie Une image Docker, c'est comme une recette de cuisine complète et figée (ingrédients + étapes). Un conteneur, c'est le plat qu'on sert à partir de cette recette. On peut servir la même recette autant de fois qu'on veut, sur n'importe quelle cuisine (serveur) qui a Docker installé — le résultat sera toujours identique.

1.2 — Images vs conteneurs

C'est LA distinction fondamentale à bien comprendre :

  • Image : un modèle en lecture seule, immuable, composé de couches (layers) empilées. Elle contient le système de fichiers minimal, les binaires, les dépendances et la configuration nécessaires à l'exécution d'une application (ex : php:8.3-fpm-alpine, ou l'image que tu construis toi-même à partir d'un Dockerfile pour ton app Laravel).
  • Conteneur : une instance en cours d'exécution d'une image, à laquelle Docker ajoute une fine couche inscriptible par-dessus (copy-on-write). C'est un processus isolé qui tourne sur le noyau de la machine hôte.

On peut lancer plusieurs conteneurs à partir d'une même image, exactement comme on peut créer plusieurs objets à partir d'une même classe en programmation orientée objet.

bash
# Une image = un modèle immuable téléchargé ou construit une fois
docker pull php:8.3-fpm-alpine

# Un conteneur = une instance de cette image, on peut en lancer plusieurs
docker run -d --name api-tenant-a php:8.3-fpm-alpine
docker run -d --name api-tenant-b php:8.3-fpm-alpine

# Les deux conteneurs partagent la même image de base,
# mais ont chacun leur propre couche inscriptible et leurs propres processus
docker ps
docker images

1.3 — Ce qui rend l'isolation possible : namespaces & cgroups

Docker ne réinvente pas la virtualisation : il s'appuie sur des fonctionnalités du noyau Linux qui existent depuis longtemps.

Les namespaces (l'isolation)

Un namespace limite ce qu'un processus peut voir. Chaque conteneur tourne dans son propre ensemble de namespaces, ce qui lui donne l'illusion d'être seul sur la machine :

NamespaceCe qu'il isoleExemple concret
pidLes processusDans le conteneur, ton process php-fpm voit son PID 1, alors qu'il a un PID différent côté hôte
netLe réseauLe conteneur app a sa propre IP interne et sa propre table de routage
mntLes points de montage / systèmes de fichiersLe conteneur ne voit que son propre système de fichiers, pas celui de l'hôte
utsLe hostnamemariadb-tenant peut avoir un hostname différent du serveur physique
ipcLa communication inter-processusEmpêche un conteneur d'accéder à la mémoire partagée d'un autre
userLes UID/GIDLe root dans le conteneur peut être mappé vers un utilisateur non privilégié sur l'hôte (rootless)

Les cgroups (les quotas)

Les control groups (cgroups) limitent ce qu'un processus peut consommer : CPU, RAM, I/O disque, bande passante réseau. C'est ce qui permet d'empêcher un conteneur MariaDB gourmand de faire tomber toute la machine.

bash
# Limiter un conteneur à 512 Mo de RAM et 1 cœur CPU
docker run -d \
  --name mariadb-tenant \
  --memory="512m" \
  --cpus="1.0" \
  mariadb:11

# Vérifier les limites appliquées (cgroups) sur un conteneur en cours d'exécution
docker inspect --format='{{.HostConfig.Memory}} bytes / {{.HostConfig.NanoCpus}} nanocpus' mariadb-tenant

# Voir les namespaces attribués à un conteneur depuis l'hôte
docker inspect --format='{{.State.Pid}}' mariadb-tenant
sudo lsns -p $(docker inspect --format='{{.State.Pid}}' mariadb-tenant)

1.4 — Architecture client-serveur de Docker

Quand tu tapes docker run, plusieurs composants entrent en jeu, et ce n'est pas de la magie :

  • Docker CLI (docker) : le client en ligne de commande que tu utilises. Il traduit tes commandes en appels API REST.
  • Docker daemon (dockerd) : le serveur qui écoute sur un socket Unix (/var/run/docker.sock) ou un port TCP. Il gère les images, conteneurs, réseaux, volumes.
  • containerd : le runtime de haut niveau, extrait de Docker et devenu un projet CNCF indépendant, qui gère le cycle de vie des conteneurs (pull d'image, démarrage, arrêt).
  • runc : le runtime de bas niveau (OCI) qui crée réellement les namespaces/cgroups et démarre le processus dans le conteneur.

                                            |
                                            v

Pourquoi c'est important en pratique Sur un VPS géré par Coolify, c'est dockerd qui tourne en permanence en arrière-plan et expose son socket. Coolify (comme Portainer, ou tes propres scripts) parle à ce daemon via l'API pour créer, démarrer et surveiller les conteneurs de tes applications. Si dockerd plante ou n'est pas démarré, Coolify perd totalement la main sur tes conteneurs — c'est souvent la première chose à vérifier (systemctl status docker) quand "rien ne répond" sur le VPS.

1.5 — Conteneurs vs machines virtuelles

C'est la confusion n°1 des débutants : un conteneur n'est pas une VM légère. Une VM virtualise du matériel et fait tourner un noyau complet ; un conteneur est un processus isolé qui partage le noyau de l'hôte.

🖥️ Machine virtuelle

  • Hyperviseur (KVM, VMware…) virtualise le matériel
  • Chaque VM a son propre noyau complet
  • Démarrage lent (dizaines de secondes, boot d'un OS entier)
  • Empreinte disque/RAM lourde (plusieurs Go)
  • Isolation très forte (frontière matérielle virtualisée)

📦 Conteneur

  • Le noyau Linux de l'hôte est partagé par tous les conteneurs
  • Isolation via namespaces + cgroups (logicielle, pas matérielle)
  • Démarrage quasi instantané (millisecondes à secondes)
  • Empreinte légère (quelques Mo à centaines de Mo)
  • Isolation logique — suffisante pour la plupart des usages, mais pas équivalente à une VM
CritèreVMConteneur Docker
NoyauDédié par VMPartagé avec l'hôte
Temps de démarrage~10-60 s~0.1-2 s
Densité par serveurQuelques dizainesDes centaines
PortabilitéImage disque lourde (.qcow2, .vmdk)Image en couches, quelques Mo à quelques centaines de Mo
Cas d'usage typiqueIsoler des OS différents, forte isolation sécuritéDéployer des services applicatifs (API, workers, bases de données)
🧩 Mise en situation — "Le conteneur voit le mauvais hostname / la mauvaise heure"
Contexte

Sur le VPS qui héberge la stack Laravel multi-tenant via Coolify, un développeur s'étonne que hostname dans le conteneur app ne corresponde pas au nom du VPS, et pense qu'il y a un bug réseau grave.

Explication

C'est un comportement normal et attendu : le namespace uts donne à chaque conteneur son propre hostname (souvent l'ID du conteneur, ou celui défini par hostname: dans le compose). Ce n'est pas le hostname de l'hôte, et ce n'est pas non plus l'hôte accessible depuis Traefik — Traefik route par nom de service Docker interne, pas par hostname système.

Vérification
bash
docker exec app hostname
docker exec app date
docker inspect --format='{{.Config.Hostname}}' app

Si l'heure est décalée, le vrai problème est souvent l'absence de synchronisation NTP sur l'hôte — les conteneurs héritent de l'horloge du noyau hôte, ils n'ont pas leur propre horloge.

Piège classique Penser qu'un docker restart "redémarre le système" du conteneur comme on rebooterait une VM. En réalité, cela arrête puis relance le process principal (PID 1) défini par CMD/ENTRYPOINT. Toute donnée écrite dans la couche inscriptible du conteneur (hors volume) est conservée entre un restart, mais perdue si le conteneur est supprimé (docker rm) puis recréé.

Dockerfile : construire ses propres images

Le Dockerfile est la recette qui décrit comment fabriquer une image. On y détaille chaque instruction, la notion de layers et de cache, les multi-stage builds, et les bonnes pratiques pour obtenir des images légères et rapides à construire — avec en fil rouge le Dockerfile d'une application Laravel + Inertia + Vue.

2.1 — Les instructions clés

InstructionRôle
FROMDéfinit l'image de base sur laquelle on part (ex : php:8.3-fpm-alpine)
WORKDIRDéfinit le répertoire de travail courant pour les instructions suivantes
COPY / ADDCopie des fichiers depuis le contexte de build vers l'image. ADD gère en plus les URL et l'extraction d'archives — préférer COPY sauf besoin spécifique
RUNExécute une commande au moment du build et crée un nouveau layer (ex : composer install)
ENVDéfinit une variable d'environnement persistante dans l'image et les conteneurs qui en découlent
ARGDéfinit une variable disponible uniquement pendant le build (ex : version PHP, token de build)
EXPOSEDocumente le port que le conteneur écoute (n'ouvre rien réellement, c'est informatif)
USERChange l'utilisateur d'exécution des instructions suivantes et du process final
VOLUMEDéclare un point de montage destiné à être persisté
LABELAjoute des métadonnées à l'image (souvent utilisé par Traefik/Coolify pour la configuration)
HEALTHCHECKDéfinit comment Docker doit vérifier que le conteneur est en bonne santé
CMDCommande par défaut exécutée au démarrage du conteneur — peut être surchargée au docker run
ENTRYPOINTCommande fixe exécutée au démarrage — CMD devient alors ses arguments par défaut
CMD vs ENTRYPOINT Utilise ENTRYPOINT pour la commande "fixe" (ex : un script d'init qui attend la base de données, applique les migrations, puis lance php-fpm), et CMD pour fournir des arguments par défaut modifiables. C'est le combo classique des images d'applications en production.

2.2 — Un premier Dockerfile simple

Dockerfiledockerfile
FROM php:8.3-fpm-alpine

WORKDIR /var/www/html

RUN apk add --no-cache libzip-dev icu-dev \
    && docker-php-ext-install pdo_mysql zip intl opcache

COPY . .

RUN composer install --no-dev --optimize-autoloader

EXPOSE 9000
CMD ["php-fpm"]

Ce Dockerfile fonctionne, mais il a plusieurs défauts qu'on va corriger au fil du chapitre : pas de gestion du cache de layers, pas de build des assets front, image finale trop lourde, exécution en root, aucun .dockerignore.

2.3 — Layers et cache de build

Chaque instruction RUN, COPY ou ADD crée un nouveau layer (une couche du système de fichiers, stockée et identifiée par un hash). Docker met en cache ces layers : si rien n'a changé pour une instruction donnée et toutes celles qui la précèdent, Docker réutilise le layer existant au lieu de le reconstruire.

Règle d'or Place les instructions qui changent le moins souvent en haut du Dockerfile, et celles qui changent le plus souvent (comme COPY . . du code source) en bas. Sinon, chaque modification de code invalide tout le cache en aval, y compris composer install ou npm ci qui redémarrent inutilement à zéro.

❌ Cache invalidé à chaque commit

dockerfile
FROM php:8.3-fpm-alpine
WORKDIR /var/www/html
COPY . .
RUN composer install --no-dev

Le moindre changement dans n'importe quel fichier du projet (même un README.md) invalide le layer COPY . ., donc composer install est rejoué intégralement — plusieurs minutes perdues à chaque build.

✅ Cache exploité intelligemment

dockerfile
FROM php:8.3-fpm-alpine
WORKDIR /var/www/html
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts
COPY . .
RUN composer dump-autoload --optimize

Tant que composer.json/composer.lock ne changent pas, l'étape coûteuse composer install reste en cache, même si le code applicatif change à chaque commit.

2.4 — Multi-stage builds

Un multi-stage build permet d'utiliser plusieurs images FROM dans un seul Dockerfile, chacune formant une "étape" (stage). On peut copier sélectivement des fichiers d'une étape à l'autre avec COPY --from=, et ne garder dans l'image finale que ce qui est réellement nécessaire à l'exécution — sans les outils de build (Node, compilateurs, dépendances de dev).

Exemple complet pour notre application Laravel + Inertia + Vue : une étape compile les assets front avec Node, une autre installe les dépendances PHP, et l'étape finale assemble uniquement le nécessaire pour tourner en production.

Dockerfiledockerfile
# ---- Étape 1 : build des assets front (Vue + Inertia via Vite) ----
FROM node:20-alpine AS frontend-builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY resources/ resources/
COPY vite.config.ts tsconfig.json ./
RUN npm run build

# ---- Étape 2 : dépendances PHP (Composer) ----
FROM composer:2 AS vendor-builder
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install \
    --no-dev \
    --no-scripts \
    --no-autoloader \
    --ignore-platform-reqs

# ---- Étape 3 : image finale de production, légère ----
FROM php:8.3-fpm-alpine AS production

RUN apk add --no-cache libzip icu-libs \
    && apk add --no-cache --virtual .build-deps libzip-dev icu-dev $PHPIZE_DEPS \
    && docker-php-ext-install pdo_mysql zip intl opcache \
    && apk del .build-deps

WORKDIR /var/www/html

# On ne récupère QUE le résultat des étapes précédentes, pas les outils de build
COPY --from=vendor-builder /app/vendor ./vendor
COPY --from=frontend-builder /app/public/build ./public/build
COPY . .

RUN composer dump-autoload --optimize --classmap-authoritative \
    && php artisan config:cache \
    && php artisan route:cache \
    && php artisan view:cache

RUN addgroup -g 1000 laravel && adduser -D -u 1000 -G laravel laravel \
    && chown -R laravel:laravel /var/www/html/storage /var/www/html/bootstrap/cache

USER laravel

EXPOSE 9000
CMD ["php-fpm"]
Pourquoi c'est puissant L'image finale ne contient ni Node.js, ni npm, ni les paquets -dev de Composer, ni les headers de compilation (libzip-dev, icu-dev) : uniquement le runtime PHP-FPM, les extensions compilées, le code applicatif et les assets déjà compilés. Résultat : une image plusieurs fois plus légère, avec une surface d'attaque réduite.

2.5 — .dockerignore : ne pas envoyer n'importe quoi au build

Le build context (tout ce que Docker envoie au daemon pour construire l'image) inclut par défaut tous les fichiers du répertoire, sauf ceux exclus par .dockerignore. Sans ce fichier, on envoie souvent node_modules, vendor, .git, les fichiers .env contenant des secrets, et les logs — ce qui ralentit le build et peut faire fuiter des informations sensibles dans l'image.

2.6 — Réduire la taille des images : checklist de bonnes pratiques

  • Partir d'une image de base minimale : alpine ou slim plutôt que l'image complète (ex : php:8.3-fpm-alpine ≈ 70 Mo vs php:8.3-fpm ≈ 480 Mo)
  • Chaîner les commandes RUN apk add ... && ... && apk del ... pour éviter des layers intermédiaires qui alourdissent l'image même après suppression des fichiers
  • Nettoyer les caches de gestionnaires de paquets dans le même RUN (rm -rf /var/cache/apk/*, rm -rf /var/lib/apt/lists/*)
  • Utiliser le multi-stage pour exclure les outils de build de l'image finale
  • Ne copier que ce qui est nécessaire (.dockerignore strict)
  • Utiliser --no-dev / --production / --omit=dev selon le gestionnaire de paquets
  • Vérifier régulièrement la taille avec docker images et docker history
bash
# Comparer la taille de deux variantes d'image
docker images | grep laravel-app

# Voir le détail layer par layer : quelle instruction ajoute combien de Mo
docker history laravel-app:latest --format "table {{.CreatedBy}}\t{{.Size}}"
🧩 Mise en situation — "Le build prend 8 minutes à chaque petit changement de code"
Contexte

Sur le pipeline qui build l'image de l'app Laravel avant déploiement via Coolify, chaque petite modification de contrôleur PHP fait repartir npm ci et composer install depuis zéro, alors qu'aucune dépendance n'a changé.

Diagnostic

Le Dockerfile fait probablement un COPY . . avant d'installer les dépendances. N'importe quel fichier modifié invalide alors le cache de tous les layers suivants, y compris les installations de dépendances.

Solution

Réordonner le Dockerfile en copiant d'abord uniquement les fichiers de verrouillage des dépendances (composer.json/composer.lock, package.json/package-lock.json), installer les dépendances, puis copier le reste du code source. Voir la comparaison "cache exploité intelligemment" ci-dessus.

Docker Compose : orchestrer plusieurs conteneurs

Une application réelle est rarement un seul conteneur : notre stack Laravel a besoin d'une base de données, d'un cache Redis, d'un worker de queue, et doit être reliée à Traefik. Docker Compose permet de décrire toute cette topologie dans un unique fichier déclaratif.

3.1 — Anatomie d'un fichier compose

Un fichier docker-compose.yml décrit des services (chacun devenant un ou plusieurs conteneurs), des réseaux, et des volumes. Depuis Compose V2, la clé version: en tête de fichier n'est plus nécessaire.

docker-compose.ymlyaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    image: laravel-app:latest
    restart: unless-stopped
    environment:
      APP_ENV: production
      DB_HOST: mariadb
      REDIS_HOST: redis
    volumes:
      - ./storage:/var/www/html/storage
    depends_on:
      mariadb:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - internal
      - traefik-public

  mariadb:
    image: mariadb:11
    restart: unless-stopped
    environment:
      MARIADB_ROOT_PASSWORD: ${DB_ROOT_PASSWORD}
      MARIADB_DATABASE: ${DB_DATABASE}
    volumes:
      - mariadb-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - internal

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    networks:
      - internal

networks:
  internal:
    driver: bridge
  traefik-public:
    external: true

volumes:
  mariadb-data:

3.2 — Services : le cœur de la description

Chaque clé sous services: devient un conteneur (ou plusieurs, si on utilise deploy.replicas en mode Swarm). Les options les plus utilisées :

CléRôle
buildConstruit l'image à partir d'un Dockerfile local plutôt que de tirer une image publiée
imageNom (et éventuellement tag) de l'image à utiliser ou à construire
restartPolitique de redémarrage automatique (voir chapitre 8)

profilesRend le service optionnel, activé seulement avec certains profils

3.3 — Variables d'environnement : bien les gérer

Trois façons de fournir des variables, à ne pas confondre :

  • environment: — variables définies en dur ou interpolées depuis le shell/le fichier .env à côté du compose
  • env_file: — charge un fichier entier de variables (ex : le .env de Laravel lui-même)
  • Interpolation ${VARIABLE} dans le YAML — résolue par Compose lui-même au moment de générer la configuration, à partir du fichier .env situé dans le même dossier que le docker-compose.yml
.env (à côté du docker-compose.yml)dotenv
DB_ROOT_PASSWORD=change_me_in_production
DB_DATABASE=laravel_saas
TENANT_DOMAIN=tenant-a.monapp.com
Piège fréquent Le .env lu par Docker Compose (pour l'interpolation ${...} dans le YAML) et le .env lu par Laravel à l'intérieur du conteneur sont deux fichiers différents, avec des rôles différents. Ne pas les confondre évite bien des heures de debug — un mot de passe changé dans l'un n'a aucun effet sur l'autre.

3.4 — depends_on et l'ordre de démarrage

depends_on contrôle l'ordre de démarrage des conteneurs, mais par défaut ne garantit pas que le service dépendant soit réellement prêt à répondre (juste que son conteneur a démarré). C'est pour cela qu'on couple depends_on à un healthcheck avec condition: service_healthy.

❌ depends_on simple

yaml
app:
  depends_on:
    - mariadb

Le conteneur app démarre dès que le conteneur mariadb a démarré — pas quand MariaDB a réellement fini son initialisation et accepte des connexions. Résultat classique : erreurs SQLSTATE[HY000] [2002] Connection refused au premier déploiement.

✅ depends_on avec condition de santé

yaml
app:
  depends_on:
    mariadb:
      condition: service_healthy

Compose attend que le healthcheck de mariadb passe à l'état healthy avant de démarrer app. Plus fiable, à condition d'avoir défini un healthcheck pertinent sur le service MariaDB.

3.5 — Les profils : activer des services à la demande

Les profiles permettent de rendre certains services optionnels : un outil de debug, un worker secondaire, un service de test, ou un tenant de démo qu'on ne veut lancer que ponctuellement.

docker-compose.yml (extrait)yaml
services:
  app:
    # ... configuration principale

  queue-worker:
    build: .
    command: php artisan queue:work --tries=3
    profiles: ["worker"]
    networks: [internal]

  mailpit:
    image: axllent/mailpit
    profiles: ["dev"]
    ports:
      - "8025:8025"
    networks: [internal]
bash
# Démarre uniquement les services sans profil (app, mariadb, redis)
docker compose up -d

# Active en plus le worker de queue et l'outil de mail de dev
docker compose --profile worker --profile dev up -d

3.6 — Commandes du quotidien

bash
docker compose up -d              # démarre tout en arrière-plan
docker compose ps                 # état des services
docker compose logs -f app        # suit les logs du service "app"
docker compose exec app bash      # ouvre un shell dans le conteneur "app"
docker compose down               # arrête et supprime les conteneurs (garde les volumes nommés)
docker compose down -v            # ATTENTION : supprime aussi les volumes nommés
docker compose config             # valide et affiche la configuration finale résolue
🧩 Mise en situation — "Le conteneur app boucle en erreur de connexion à la base au démarrage"
Contexte

Après un docker compose up -d sur le VPS, le conteneur app redémarre en boucle avec dans les logs : SQLSTATE[HY000] [2002] Connection refused.

Logs observés
output
$ docker compose logs app --tail=20

MariaDB est encore en phase d'initialisation (health: starting) quand app tente déjà de s'y connecter. Le depends_on n'utilisait probablement pas de condition service_healthy.

Solution

Ajouter un healthcheck réaliste sur le service mariadb et faire dépendre app de sa condition service_healthy (voir 3.4). En complément, on peut ajouter une logique de retry côté application (ex : un script d'entrypoint qui attend la base avant de lancer php-fpm), utile aussi en cas de redémarrage isolé de MariaDB sans passer par compose up.

Réseau Docker

Comprendre le réseau Docker est indispensable pour comprendre comment Traefik route le trafic vers tes conteneurs applicatifs. On y voit les types de réseaux, la résolution DNS interne, l'exposition de ports, et comment les conteneurs communiquent entre eux.

4.1 — Les drivers réseau principaux

DriverUsage
bridgeRéseau local virtuel sur un seul hôte Docker. C'est le driver par défaut, celui utilisé sur un VPS Coolify mono-nœud
overlayRéseau virtuel qui s'étend sur plusieurs hôtes Docker (Swarm/cluster) — permet à des conteneurs sur des machines physiques différentes de se parler comme s'ils étaient sur le même réseau local
hostLe conteneur partage directement la pile réseau de l'hôte (pas d'isolation réseau) — rare, utilisé pour des cas de performance très spécifiques
noneAucune interface réseau — isolation totale
macvlanAttribue une adresse MAC propre au conteneur sur le réseau physique — cas avancés d'intégration réseau

Sur un simple VPS (le cas typique de Coolify), on reste presque toujours en bridge. L'overlay devient pertinent seulement en Swarm multi-nœuds (voir chapitre 8).

4.2 — Le réseau bridge par défaut vs les réseaux définis par l'utilisateur

Docker crée un réseau bridge par défaut (souvent nommé docker0), mais son usage est déconseillé en pratique : il n'offre pas de résolution DNS par nom de conteneur, seulement par adresse IP (qui change à chaque redémarrage). Les réseaux définis par l'utilisateur (créés via docker network create ou automatiquement par Compose) résolvent les noms de service/conteneur via un DNS interne.

bash
# Lister les réseaux existants
docker network ls

# Créer un réseau dédié pour que Traefik puisse joindre les conteneurs de l'app
docker network create traefik-public

# Inspecter un réseau : quels conteneurs y sont connectés, quelles IP
docker network inspect traefik-public

4.3 — DNS interne : se parler par nom de service

Sur un réseau défini par l'utilisateur (ou créé par Compose), chaque conteneur peut joindre les autres par leur nom de service, sans jamais connaître leur adresse IP. C'est le mécanisme qui permet à Laravel de se connecter à MariaDB via DB_HOST=mariadb plutôt qu'une IP.

bash
# Depuis le conteneur "app", on peut joindre "mariadb" et "redis" par leur nom
docker compose exec app getent hosts mariadb
docker compose exec app ping -c 2 redis
docker compose exec app nc -zv mariadb 3306
Comment Traefik s'appuie sur ce mécanisme Traefik écoute le socket Docker, détecte les conteneurs qui portent des labels Traefik, et route le trafic HTTP vers eux en utilisant ce même DNS interne — à condition que le conteneur applicatif et le conteneur Traefik soient rattachés au même réseau Docker (généralement un réseau externe partagé, ex : traefik-public, que Coolify crée et attache automatiquement à chaque application déployée).

4.4 — Exposition de ports : EXPOSE, ports, et Traefik

Trois notions à ne pas confondre :

  • EXPOSE dans le Dockerfile : purement documentaire, n'ouvre rien
  • ports: dans le compose (ou -p en CLI) : publie réellement un port du conteneur sur l'hôte, le rendant accessible depuis l'extérieur de Docker
  • Communication interne inter-conteneurs (sur le même réseau) : ne nécessite aucun ports: — les conteneurs se joignent directement par leur port interne via le DNS
Bonne pratique avec Traefik Le conteneur applicatif (PHP-FPM ou Nginx de l'app) n'a en général aucune raison de publier un port sur l'hôte (ports: vide). Seul Traefik publie les ports 80/443 sur l'hôte, et route ensuite le trafic en interne vers le bon conteneur via le réseau Docker partagé et ses labels. Cela réduit la surface d'attaque : rien n'est accessible directement, tout passe par le reverse proxy.
docker-compose.yml (extrait, labels Traefik)yaml
services:
  app:
    build: .
    networks:
      - traefik-public
      - internal
    labels:
      traefik.enable: "true"
      traefik.http.routers.tenant-a.rule: "Host(`tenant-a.monapp.com`)"
      traefik.http.routers.tenant-a.entrypoints: "websecure"
      traefik.http.routers.tenant-a.tls.certresolver: "letsencrypt"
      traefik.http.services.tenant-a.loadbalancer.server.port: "80"

networks:
  traefik-public:
    external: true
  internal:
    driver: bridge

4.5 — Bridge vs overlay : pourquoi ça compte pour Traefik

🌉 Bridge (VPS mono-nœud)

  • Tous les conteneurs (app, DB, Redis, Traefik) tournent sur la même machine
  • Le réseau bridge suffit largement — c'est la configuration Coolify standard
  • DNS interne résolu directement par le daemon Docker local

🕸️ Overlay (cluster Swarm multi-nœuds)

  • Les conteneurs peuvent être répartis sur plusieurs machines physiques
  • Un réseau overlay chiffré (VXLAN) permet la communication inter-hôtes
  • Nécessaire seulement si on scale horizontalement sur plusieurs VPS (voir chapitre 8)
🧩 Mise en situation — "Traefik renvoie 502 Bad Gateway pour le sous-domaine d'un nouveau tenant"
Contexte

Un nouveau tenant est créé, son sous-domaine tenant-c.monapp.com résout bien vers l'IP du VPS (DNS wildcard *.monapp.com déjà en place), mais Traefik renvoie une erreur 502 Bad Gateway.

Hypothèses à vérifier dans l'ordre
  1. Le conteneur applicatif du tenant est-il démarré ? (docker ps | grep tenant-c)
  2. Le conteneur est-il rattaché au même réseau Docker que Traefik (traefik-public) ?
  3. Les labels Traefik pointent-ils vers le bon port interne exposé par le conteneur applicatif ?
bash
docker ps --filter "name=tenant-c"
docker network inspect traefik-public --format '{{range .Containers}}{{.Name}} {{end}}'
docker inspect tenant-c-app --format '{{json .Config.Labels}}' | python3 -m json.tool
docker logs traefik --tail 50 | grep -i tenant-c
Cause fréquente

Le conteneur de l'app a bien démarré, mais uniquement sur le réseau internal (pour parler à sa base de données), sans être aussi rattaché à traefik-public. Traefik "voit" le conteneur via l'API Docker, génère une route, mais ne peut physiquement pas atteindre son IP puisqu'ils ne partagent aucun réseau commun → 502.

Solution

Ajouter le réseau traefik-public à la liste des networks: du service applicatif, puis recréer le conteneur (docker compose up -d --force-recreate app).

Volumes et persistance des données

Les conteneurs sont éphémères par nature : leur couche inscriptible disparaît quand on les supprime. Pour conserver des données importantes (base de données, fichiers uploadés par les tenants), il faut sortir cette donnée du cycle de vie du conteneur — c'est le rôle des volumes.

5.1 — Pourquoi la donnée ne doit jamais vivre "dans" le conteneur

Règle non négociable Un conteneur est fait pour être détruit et recréé à tout moment (déploiement, mise à jour d'image, migration vers un nouveau VPS). Toute donnée écrite uniquement dans la couche inscriptible du conteneur — et pas dans un volume ou un bind mount — sera perdue définitivement au premier docker rm ou docker compose down. C'est vrai pour les fichiers de MariaDB (/var/lib/mysql), pour les fichiers uploadés par les tenants (storage/app/public), et pour les sessions/cache si on ne veut pas les perdre.

5.2 — Bind mounts vs volumes nommés

CritèreBind mountVolume nommé
EmplacementChemin choisi sur l'hôte (./storage:/app/storage)Géré par Docker, dans /var/lib/docker/volumes/...
PortabilitéDépend de la structure de fichiers de l'hôtePortable, indépendant du chemin hôte
Cas d'usage typiqueCode source en dev (hot-reload), fichiers de config précisDonnées de base de données, données de service qui n'ont pas besoin d'être "vues" facilement depuis l'hôte
PermissionsHéritent des permissions du dossier hôte (source fréquente de conflits UID/GID)Gérées par Docker, généralement plus prévisibles
SauvegardeSimple : c'est un dossier normal sur l'hôteNécessite un conteneur ou docker run --volumes-from pour y accéder
docker-compose.yml (extrait)yaml
services:
  app:
    volumes:
      # Bind mount : utile en dev pour voir le code modifié sans rebuild
      - ./storage/app/public:/var/www/html/storage/app/public

  mariadb:
    volumes:
      # Volume nommé : Docker gère l'emplacement, plus robuste en prod
      - mariadb-data:/var/lib/mysql

volumes:
  mariadb-data:
    driver: local
Recommandation pour la stack multi-tenant En production : volumes nommés pour les données critiques de bases de données (MariaDB, Redis en mode persistant), et bind mounts uniquement pour ce qui a besoin d'être facilement inspecté/sauvegardé depuis l'hôte (fichiers uploadés par tenant, souvent organisés par sous-dossier storage/tenants/{tenant-id}/).

5.3 — Gérer les volumes au quotidien

bash
# Lister tous les volumes
docker volume ls

# Inspecter un volume : où est-il physiquement stocké sur l'hôte ?
docker volume inspect projet_mariadb-data

# ATTENTION : commande destructrice, supprime les volumes non utilisés par aucun conteneur
docker volume prune

# Voir l'espace disque utilisé par les volumes
docker system df -v

5.4 — Stratégies de backup

Un volume Docker n'est pas une sauvegarde en soi : il protège seulement des cycles de vie du conteneur, pas d'une panne disque, d'une suppression accidentelle, ou d'une corruption. Il faut une vraie stratégie de backup.

Backup d'une base MariaDB via dump logique (recommandé pour la portabilité)

bash
# Dump complet, compressé, horodaté
docker compose exec -T mariadb \
  mysqldump -u root -p"$DB_ROOT_PASSWORD" --all-databases \
  | gzip > "backup-$(date +%Y%m%d-%H%M%S).sql.gz"

# Restauration à partir d'un dump
gunzip -c backup-20260115-020000.sql.gz | docker compose exec -T mariadb \
  mysql -u root -p"$DB_ROOT_PASSWORD"

Backup au niveau volume (snapshot binaire, plus rapide mais moins portable)

bash
# Archive un volume nommé dans un tarball, via un conteneur temporaire jetable
docker run --rm \
  -v projet_mariadb-data:/data:ro \
  -v "$(pwd)/backups":/backup \
  alpine \
  tar czf /backup/mariadb-data-$(date +%Y%m%d).tar.gz -C /data .

Backup des fichiers tenants (bind mount)

bash
# rsync incrémental vers un stockage distant (ex: un second VPS ou un bucket S3-compatible)
rsync -avz --delete \
  ./storage/tenants/ \
  backup-user@backup-server:/backups/monapp/tenants/
  • Automatiser les backups via un cron sur l'hôte (ou un conteneur planificateur) — jamais de backup manuel en production
  • Toujours tester la restauration, pas seulement la sauvegarde (un backup jamais testé n'est pas fiable)
  • Stocker les backups hors du VPS de production (autre serveur, stockage objet) pour survivre à une panne matérielle totale
  • Chiffrer les backups contenant des données personnelles de tenants (RGPD)
  • Documenter et versionner la rétention (ex : quotidien 7 jours, hebdomadaire 4 semaines, mensuel 12 mois)
🧩 Mise en situation — "Après une mise à jour, toutes les données des tenants ont disparu"
Contexte

Un développeur modifie le docker-compose.yml pour "nettoyer" la configuration, relance avec docker compose down -v puis docker compose up -d. Toutes les données MariaDB ont disparu.

Cause

Le flag -v de docker compose down supprime également tous les volumes nommés déclarés dans le fichier compose — pas seulement les conteneurs et réseaux. C'est une commande à utiliser avec une extrême prudence, quasiment jamais en production.

Bonne pratique

En production, préférer systématiquement docker compose down (sans -v) ou même éviter complètement down au profit de docker compose up -d --force-recreate pour les mises à jour, qui ne touche jamais aux volumes.

Build avancé : BuildKit, cache distant et diagnostics

Une fois les bases du Dockerfile maîtrisées, on peut exploiter BuildKit pour accélérer drastiquement les builds en CI/CD, partager du cache entre machines, et savoir diagnostiquer les erreurs de build les plus déroutantes — comme le fameux ETXTBSY.

6.1 — BuildKit : le moteur de build moderne

Depuis Docker 23+, BuildKit est le moteur de build par défaut (il l'était déjà en option depuis Docker 18.09). Il remplace l'ancien "legacy builder" et apporte :

  • Une résolution de dépendances entre étapes plus intelligente, permettant l'exécution parallèle des étapes indépendantes d'un multi-stage build
  • Des caches de montage (--mount=type=cache) persistants entre builds, sans polluer les layers de l'image finale
  • L'export/import de cache distant (registre, GitHub Actions cache…), très utile en CI
  • Un frontend .dockerfile extensible (syntaxes alternatives via # syntax=)
bash
# Vérifier que BuildKit est actif (Docker 23+ : actif par défaut)
docker buildx version

# Forcer BuildKit sur une ancienne version de Docker si besoin
export DOCKER_BUILDKIT=1
docker build -t laravel-app .

6.2 — Cache de montage : accélérer composer/npm sans alourdir l'image

Le cache mount permet de conserver un cache (ex : le cache Composer, le cache npm) entre plusieurs builds, sans que ce cache ne se retrouve dans les layers de l'image finale — contrairement à un RUN composer install classique où le cache téléchargé reste piégé dans le layer tant qu'on ne le nettoie pas explicitement.

Dockerfile (extrait)dockerfile
# syntax=docker/dockerfile:1

FROM composer:2 AS vendor-builder
WORKDIR /app
COPY composer.json composer.lock ./
RUN --mount=type=cache,target=/tmp/cache/composer,sharing=locked \
    composer config -g cache-dir /tmp/cache/composer \
    && composer install --no-dev --no-scripts --no-autoloader

FROM node:20-alpine AS frontend-builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm,sharing=locked \
    npm ci

Le cache est stocké par BuildKit lui-même (hors des layers de l'image) et réutilisé automatiquement au prochain build — même si le code source a changé — tant que la machine (ou le cache distant partagé) reste la même.

6.3 — Cache distant : partager le cache entre CI et machines différentes

Sur un runner CI éphémère (GitHub Actions, GitLab CI), le cache local de BuildKit disparaît à chaque run. On peut exporter/importer le cache via un registre d'images, pour que le prochain build (même sur une machine différente) en profite.

bash
# Build en exportant le cache vers le registre, en plus de l'image elle-même
docker buildx build \
  --cache-to type=registry,ref=registry.example.com/laravel-app:cache,mode=max \
  --cache-from type=registry,ref=registry.example.com/laravel-app:cache \
  -t registry.example.com/laravel-app:latest \
  --push .
mode=max vs mode=min mode=min n'exporte que le cache des layers finaux, mode=max exporte le cache de toutes les étapes intermédiaires d'un multi-stage build — plus volumineux à stocker, mais bien plus efficace quand on veut réutiliser le cache des étapes de build front/vendor entre deux pipelines CI différents.

6.4 — Nettoyer le cache de build : docker builder prune

Le cache de BuildKit grossit avec le temps et peut occuper plusieurs dizaines de Go sur un VPS avec des builds fréquents (déploiements Coolify réguliers). Il faut le nettoyer régulièrement.

bash
# Voir l'espace disque utilisé par le cache de build
docker system df

# Supprimer le cache de build inutilisé depuis plus de 48h
docker builder prune --filter until=48h

# Nettoyage plus agressif (tout le cache non utilisé par un build en cours)
docker builder prune -a -f

# Nettoyage global : images non utilisées, conteneurs arrêtés, réseaux orphelins, cache de build
docker system prune -a --volumes -f
Attention avec --volumes docker system prune --volumes supprime aussi les volumes anonymes et non utilisés. Sur un VPS de production, toujours vérifier au préalable avec docker system df -v et docker volume ls qu'aucune donnée importante n'est concernée avant de lancer un nettoyage automatisé (par exemple dans un cron).

6.5 — Diagnostiquer les race conditions type ETXTBSY

ETXTBSY ("Text file busy") est une erreur du noyau Linux qui survient quand un processus tente d'écrire ou remplacer un fichier binaire/exécutable en cours d'exécution ou mmap'é en mode exécutable par un autre processus. C'est rare en usage normal, mais devient plus fréquent avec Docker à cause de son système de fichiers en couches (overlay2) et de la copie-à-l'écriture.

output
$ npm ci
cp: cannot create regular file '/app/node_modules/.bin/vite': Text file busy
npm ERR! code ETXTBSY
npm ERR! syscall open
🧩 Mise en situation — "Des builds échouent aléatoirement avec ETXTBSY sur le runner CI"
Contexte

Le pipeline qui build l'image Laravel échoue de façon intermittente (pas systématique) sur l'étape npm ci, avec une erreur ETXTBSY lors de la copie d'un binaire dans node_modules/.bin. Le problème disparaît en relançant le build.

Cause racine typique

Sur le pilote de stockage overlay2, quand plusieurs builds/conteneurs démarrent en parallèle sur le même hôte et partagent des layers d'image de base (ex : plusieurs jobs CI simultanés utilisant la même image node:20-alpine), une opération de copy-up (copie d'un fichier de la couche en lecture seule vers la couche inscriptible au moment où il est modifié) peut entrer en conflit avec un autre processus qui a déjà ouvert ce même fichier en exécution — provoquant un ETXTBSY transitoire.

Facteurs aggravants
  • Builds fortement parallélisés (plusieurs jobs CI sur le même runner/hôte au même instant)
  • Beaucoup de petits fichiers binaires (le dossier .bin/ de npm, plein de liens symboliques et petits exécutables)
  • Un hôte avec une version de noyau ancienne présentant des bugs connus dans l'implémentation d'overlayfs
Solutions concrètes
  1. Limiter le parallélisme des builds sur le même hôte CI (éviter que 5 jobs ne construisent en même temps la même image de base sur la même machine)
  2. Retry automatique de l'étape concernée dans le pipeline — c'est un incident transitoire, pas une erreur de code
  3. Mettre à jour le noyau et Docker vers des versions récentes où ces races d'overlayfs sont corrigées
  4. Utiliser des caches de montage BuildKit (6.2) plutôt que de recopier node_modules depuis une image de base à chaque fois, ce qui réduit le nombre d'opérations de copy-up concurrentes
  5. En dernier recours, changer de driver de stockage (rare, à réserver à des hôtes dédiés au build)
À retenir sur ETXTBSY Ce n'est presque jamais un bug dans le code applicatif : c'est un symptôme de contention au niveau du système de fichiers, exacerbé par la nature en couches de Docker. Face à une erreur ETXTBSY intermittente, la première question à se poser est "qu'est-ce qui tourne en parallèle sur cet hôte au même moment ?", pas "qu'est-ce qui a changé dans le code ?".

Chapitre 7 / 11 — Niveau avancé

Sécurité

Un conteneur mal configuré peut devenir un vecteur d'attaque sérieux, notamment sur un VPS multi-tenant où l'isolation entre clients est un enjeu de confidentialité. Ce chapitre couvre les fondamentaux de durcissement : utilisateurs non-root, scan de vulnérabilités, gestion des secrets, et le mode rootless.

7.1 — Ne jamais tourner en root dans le conteneur

Par défaut, si aucun USER n'est précisé, un conteneur tourne en root. Si un attaquant parvient à exécuter du code arbitraire dans le conteneur (ex : une faille d'upload de fichier exploitée sur une app tenant), il obtient les pleins pouvoirs à l'intérieur du conteneur, et dans certains scénarios d'échappement de conteneur (moins fréquents mais existants), potentiellement des pouvoirs élevés sur l'hôte.

Dockerfile (extrait)dockerfile
FROM php:8.3-fpm-alpine

# Créer un utilisateur applicatif dédié, non privilégié
RUN addgroup -g 1000 laravel \
    && adduser -D -u 1000 -G laravel laravel

WORKDIR /var/www/html
COPY --chown=laravel:laravel . .

# Toutes les instructions suivantes (et le process final) s'exécutent en tant que "laravel"
USER laravel

CMD ["php-fpm"]
Cas particulier : php-fpm Le master process de php-fpm doit parfois rester en root pour pouvoir créer ses workers avec les bons privilèges, en configurant user/group dans www.conf plutôt qu'avec l'instruction USER du Dockerfile. Vérifie la documentation de l'image de base utilisée : certaines images officielles gèrent déjà correctement cette bascule de privilèges pour toi.

7.2 — Scanner les vulnérabilités des images

Une image contient des paquets système et des dépendances applicatives qui peuvent avoir des CVE connues. Il faut scanner régulièrement, en particulier avant chaque déploiement en production.

bash
# Scan intégré à Docker (utilise Docker Scout)
docker scout cves laravel-app:latest

# Alternative open source largement utilisée : Trivy
trivy image laravel-app:latest

# Se concentrer sur les vulnérabilités critiques/hautes uniquement
trivy image --severity CRITICAL,HIGH laravel-app:latest

# Intégrer le scan dans le pipeline CI (échoue le build si CVE critique détectée)
trivy image --exit-code 1 --severity CRITICAL laravel-app:latest
Bonne pratique CI/CD Ajoute une étape de scan avant le déploiement via Coolify, pas après. Un pipeline qui bloque un déploiement sur une CVE critique coûte quelques minutes ; une vulnérabilité exploitée en production sur une base multi-tenant peut coûter la confidentialité des données de tous les clients.

7.3 — Gestion des secrets : ce qu'il ne faut jamais faire

❌ Secrets en dur dans le Dockerfile

dockerfile
ENV DB_PASSWORD=SuperSecret123
RUN composer config --auth http-basic.repo.packagist.com user "MotDePasse"

Ces valeurs restent indéfiniment visibles dans l'historique des layers de l'image (docker history), même si on les "supprime" dans une instruction ultérieure. N'importe qui ayant accès à l'image peut les extraire.

✅ Secrets via BuildKit ou runtime

dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=composer_token \
    COMPOSER_AUTH="$(cat /run/secrets/composer_token)" composer install

Le secret est monté temporairement pendant l'exécution de l'instruction RUN, jamais persisté dans un layer. Pour les secrets d'exécution (mots de passe de base de données), on les injecte via variables d'environnement au runtime (fichier .env non commité, ou gestionnaire de secrets de la plateforme de déploiement), jamais dans l'image elle-même.

bash
# Build avec un secret transmis de façon éphémère, non persisté dans l'image
docker buildx build \
  --secret id=composer_token,src=./secrets/composer_token.txt \
  -t laravel-app .
Avec Coolify Coolify gère nativement les variables d'environnement/secrets par application (et par tenant si tu as une app par tenant), injectées au runtime sans jamais transiter par le Dockerfile ni être commitées dans le dépôt Git. C'est l'approche à privilégier plutôt que de gérer des fichiers .env manuellement sur le VPS.

7.4 — Rootless mode : Docker et la comparaison avec Podman

Par défaut, le daemon Docker (dockerd) tourne en root sur l'hôte. Le mode rootless permet de faire tourner le daemon (et donc tous les conteneurs) sous un utilisateur non privilégié, réduisant l'impact d'une éventuelle faille dans le daemon lui-même.

Faut-il migrer vers Podman ou le rootless ? Pour une stack Laravel/Coolify déployée sur un VPS dédié où tu maîtrises l'accès, le gain sécuritaire du rootless/Podman est réel mais doit être mis en balance avec la maturité de l'écosystème (Coolify est conçu autour de Docker classique). Le plus souvent, on obtient déjà un excellent niveau de sécurité avec : utilisateurs non-root dans les conteneurs, scan de CVE systématique, secrets bien gérés, et un accès SSH au VPS strictement limité — avant même d'envisager un changement d'exécuteur de conteneurs.

7.5 — Autres bonnes pratiques de durcissement

  • Utiliser read_only: true sur les services qui n'ont pas besoin d'écrire sur leur système de fichiers (avec des volumes explicites pour ce qui doit persister)
  • Supprimer les capacités Linux inutiles avec cap_drop: [ALL] puis n'ajouter que celles nécessaires (cap_add)
  • Ne jamais utiliser privileged: true sauf nécessité technique absolue et comprise
  • Limiter les ressources (CPU/RAM) pour éviter qu'un conteneur compromis ou en boucle n'épuise les ressources des autres tenants
  • Isoler chaque tenant sur son propre réseau interne quand la sensibilité des données le justifie
  • Maintenir les images de base à jour (rebuild régulier, même sans changement de code, pour absorber les correctifs de sécurité upstream)
🧩 Mise en situation — "Le scanner de sécurité du pipeline bloque le déploiement sur une CVE dans une image de base"
Contexte

Le pipeline CI/CD échoue avec trivy image --exit-code 1 --severity CRITICAL, pointant une CVE critique dans une bibliothèque système de l'image php:8.3-fpm-alpine utilisée.

Démarche
  1. Vérifier si une version plus récente du tag corrige déjà la CVE (les images officielles sont rebuild régulièrement) : docker pull php:8.3-fpm-alpine puis re-scanner
  2. Si la CVE concerne un paquet non utilisé par l'application, évaluer si elle est réellement exploitable dans ce contexte
  3. En dernier recours, documenter une exception temporaire dans la configuration du scanner, avec une date de réexamen — jamais une exception permanente et silencieuse

Ne jamais désactiver purement et simplement le scan pour "débloquer" un déploiement urgent : c'est le début d'une dérive qui rend le contrôle inutile à moyen terme.

Orchestration légère

Avant d'envisager Kubernetes, il existe des mécanismes bien plus simples pour rendre une stack Docker résiliente : les healthchecks, les restart policies, et — pour aller plus loin sur plusieurs machines — Docker Swarm, l'orchestrateur natif de Docker.

8.1 — Healthchecks : au-delà de "le conteneur tourne"

Un conteneur peut être à l'état Up tout en étant fonctionnellement mort (ex : php-fpm qui tourne mais qui n'arrive plus à se connecter à la base, ou un processus zombie). Le HEALTHCHECK exécute périodiquement une commande pour vérifier l'état réel du service.

Dockerfile (extrait)dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
  CMD php artisan health:check || exit 1
docker-compose.yml (extrait)yaml
services:
  app:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost/up"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 20s

  mariadb:
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3
ParamètreRôle
intervalFréquence d'exécution du test
timeoutDélai maximum avant de considérer le test comme échoué
retriesNombre d'échecs consécutifs avant de marquer le conteneur unhealthy
start_periodPériode de grâce au démarrage, pendant laquelle les échecs ne comptent pas (utile pour laisser le temps à une appli de "chauffer")
Pourquoi c'est crucial avec Traefik Un healthcheck bien conçu combiné à depends_on: condition: service_healthy (chapitre 3) évite les 502 temporaires au démarrage. Certaines configurations Traefik peuvent aussi s'appuyer sur l'état de santé Docker pour retirer temporairement un conteneur défaillant de la rotation, si plusieurs instances tournent derrière le même routeur.

8.2 — Restart policies : que faire quand un conteneur s'arrête

PolitiqueComportement
noNe redémarre jamais automatiquement (par défaut)
alwaysRedémarre systématiquement, y compris après un redémarrage manuel du daemon Docker ou du VPS
on-failure[:N]Redémarre uniquement si le conteneur s'arrête avec un code de sortie non nul, jusqu'à N fois maximum si précisé
unless-stoppedRedémarre toujours, sauf si le conteneur a été explicitement arrêté par un humain (docker stop) — c'est le choix recommandé pour la plupart des services applicatifs en production
docker-compose.yml (extrait)yaml
services:
  app:
    restart: unless-stopped
  mariadb:
    restart: unless-stopped
  redis:
    restart: unless-stopped
🧩 Mise en situation — "Le conteneur redémarre en boucle sans jamais se stabiliser"
Contexte

docker ps montre le conteneur app avec un statut qui oscille entre Restarting et Exited, en boucle, sur un tenant précis.

output
$ docker ps -a --filter "name=tenant-x"
CONTAINER ID   STATUS
a1b2c3d4e5f6   Restarting (1) 4 seconds ago

$ docker logs tenant-x-app --tail 30
[error] artisan: Uncaught PDOException: SQLSTATE[HY000] [1045] Access denied

Diagnostic

Le process principal (CMD) plante immédiatement à chaque démarrage (ici : mauvais mot de passe base de données pour ce tenant précis). La politique restart: unless-stopped relance le conteneur en boucle, générant un volume de logs important sans jamais résoudre le problème sous-jacent.

Solution

Corriger la cause racine (ici, la variable d'environnement de mot de passe pour ce tenant), puis docker compose up -d --force-recreate. Pour éviter le bruit en attendant le diagnostic, on peut temporairement figer le conteneur avec docker update --restart=no tenant-x-app puis l'inspecter tranquillement en le démarrant manuellement.

8.3 — Docker Swarm : l'orchestrateur natif, en survol

Docker Swarm est le mode d'orchestration intégré à Docker (pas besoin d'installer quoi que ce soit d'externe). Il permet de gérer un cluster de plusieurs hôtes Docker, avec répartition de charge, mise à jour progressive (rolling update), et tolérance de panne. Il est bien plus simple à opérer que Kubernetes, au prix de fonctionnalités plus limitées.

bash
# Initialiser un cluster Swarm sur le premier nœud (le "manager")
docker swarm init --advertise-addr 

# Sur chaque nœud "worker" additionnel, exécuter le token fourni par la commande précédente
docker swarm join --token SWMTKN-1-xxxx :2377

# Déployer une pile complète à partir d'un fichier compose
docker stack deploy -c docker-compose.yml laravel-stack

# Faire évoluer le nombre de réplicas d'un service à la volée
docker service scale laravel-stack_app=3

# Mise à jour progressive sans coupure de service
docker service update --image laravel-app:v2 laravel-stack_app
Swarm et notre stack Coolify Coolify fonctionne nativement en mode Docker "simple" (un hôte, ou plusieurs hôtes gérés indépendamment), pas en Swarm. Swarm devient pertinent si l'on sort du périmètre de Coolify pour opérer soi-même un vrai cluster multi-nœuds avec répartition de charge native — un changement d'architecture significatif, à ne considérer que si un unique VPS ne suffit vraiment plus (charge, disponibilité).

Debugging & observabilité

Savoir déployer ne suffit pas : il faut savoir diagnostiquer rapidement quand quelque chose ne va pas. Ce chapitre couvre l'arsenal d'outils du quotidien pour investiguer un incident sur la stack multi-tenant, du plus simple au plus poussé.

9.1 — docker logs : la première étape, toujours

bash
# Suivre les logs en direct
docker logs -f tenant-a-app

# Les 100 dernières lignes seulement
docker logs --tail 100 tenant-a-app

# Logs depuis un instant précis (utile pour corréler avec un pic dans le monitoring)
docker logs --since "2026-01-15T14:30:00" --until "2026-01-15T14:45:00" tenant-a-app

# Avec horodatage explicite sur chaque ligne
docker logs -t tenant-a-app

# Filtrer les erreurs applicatives Laravel
docker logs tenant-a-app 2>&1 | grep -i "exception\|error"
Où vont les logs, exactement ? Par défaut, Docker capture la sortie stdout/stderr du process principal (PID 1) via le driver de logging json-file. Si ton application Laravel écrit ses logs dans storage/logs/laravel.log plutôt que sur stdout, docker logs ne les affichera pas — il faudra soit rediriger la config de logging Laravel vers stderr/stdout en conteneur, soit consulter le fichier via docker exec.

9.2 — docker exec : entrer dans un conteneur en cours d'exécution

bash
# Ouvrir un shell interactif
docker exec -it tenant-a-app sh

# Exécuter une commande artisan directement, sans shell interactif
docker exec tenant-a-app php artisan tenants:list

# Consulter le fichier de log applicatif Laravel depuis l'intérieur du conteneur
docker exec tenant-a-app tail -n 100 storage/logs/laravel.log

# Vérifier la connectivité vers la base depuis le conteneur applicatif
docker exec tenant-a-app php artisan db:show
Limite importante docker exec ne fonctionne que si le conteneur cible est en cours d'exécution. S'il redémarre en boucle (chapitre 8), il faut d'abord le stabiliser (docker update --restart=no puis démarrage manuel) pour pouvoir l'inspecter tranquillement de l'intérieur.

9.3 — docker inspect : la vérité brute sur la configuration

docker inspect renvoie un JSON exhaustif décrivant la configuration exacte d'un conteneur, d'une image, d'un réseau ou d'un volume — sans interprétation, juste les faits.

bash
# Récupérer uniquement les variables d'environnement effectives
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' tenant-a-app

# Récupérer les réseaux auxquels un conteneur est réellement connecté
docker inspect --format '{{json .NetworkSettings.Networks}}' tenant-a-app | python3 -m json.tool

# Vérifier l'état de santé détaillé (utile pour comprendre pourquoi un healthcheck échoue)
docker inspect --format '{{json .State.Health}}' tenant-a-app | python3 -m json.tool

# Vérifier les limites de ressources appliquées
docker inspect --format 'Memory: {{.HostConfig.Memory}} bytes | CPUs: {{.HostConfig.NanoCpus}}' tenant-a-app

9.4 — Limites de ressources : surveiller la consommation en temps réel

bash
# Vue temps réel façon "top" pour tous les conteneurs
docker stats

# Vue ponctuelle, sans streaming, formatée
docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.MemPerc}}"
output

9.5 — Monitoring : passer du réactif au proactif

docker stats est utile en investigation ponctuelle, mais ne remplace pas un vrai monitoring continu avec historique et alertes. Stack open source courante pour une infra Docker/Coolify :

  • cAdvisor ou l'exporter Docker de Prometheus : collecte des métriques CPU/RAM/réseau par conteneur
  • Prometheus : stockage des séries temporelles de métriques
  • Grafana : dashboards et alerting visuel
  • Loki ou une stack ELK/EFK : centralisation et recherche dans les logs de tous les conteneurs
Coolify inclut déjà une partie du nécessaire Coolify expose des métriques CPU/RAM basiques et centralise les logs par application dans son interface. Pour une stack multi-tenant avec des exigences de SLA plus fines (alerting par tenant, historique long terme), il reste pertinent de brancher une stack Prometheus/Grafana dédiée en complément.
🧩 Mise en situation — "Un cache corrompu fait planter l'application après un déploiement"
Contexte

Après un déploiement Coolify, plusieurs tenants renvoient une page blanche ou une erreur 500, avec un message Laravel évoquant un fichier de config caché introuvable ou corrompu.

output
$ docker exec tenant-a-app tail -n 30 storage/logs/laravel.log

S'assurer que toutes les variables d'environnement nécessaires sont bien disponibles au moment du build de l'image (pas seulement au runtime), ou déplacer les commandes *:cache dans le script d'entrypoint exécuté au démarrage du conteneur plutôt qu'au moment du build — au prix d'un léger surcoût au démarrage, mais avec la garantie que le cache est toujours généré dans le bon contexte d'exécution.

10.2 — Coolify + Traefik : reverse proxy, SSL wildcard, sous-domaines par tenant

Coolify orchestre Docker à ta place et configure automatiquement Traefik via des labels générés dynamiquement, sur le même principe que ceux vus au chapitre 4. Pour une architecture multi-tenant avec un sous-domaine par client, deux approches courantes :

Un conteneur applicatif par tenant

  • Isolation forte (crash d'un tenant sans impact sur les autres)
  • Un routeur Traefik distinct par sous-domaine, chacun avec sa propre règle Host(...)
  • Plus de conteneurs à gérer, empreinte ressources plus importante

Une seule application, résolution du tenant par sous-domaine

  • Un seul jeu de conteneurs, Laravel détermine le tenant via le header Host à l'exécution (middleware de résolution de tenant)
  • Un seul routeur Traefik avec une règle HostRegexp capturant tous les sous-domaines
  • Plus économe en ressources, isolation applicative plutôt qu'au niveau conteneur
docker-compose.yml (extrait, routage multi-tenant par sous-domaine avec certificat wildcard)yaml
services:
  app:
    image: registry.example.com/laravel-app:latest
    networks: [traefik-public, internal]
    labels:
      traefik.enable: "true"
      traefik.http.routers.app.rule: "HostRegexp(`^[a-z0-9-]+\\.monapp\\.com$`)"
      traefik.http.routers.app.entrypoints: "websecure"
      traefik.http.routers.app.tls.certresolver: "letsencrypt"
      traefik.http.routers.app.tls.domains[0].main: "monapp.com"
      traefik.http.routers.app.tls.domains[0].sans: "*.monapp.com"
      traefik.http.services.app.loadbalancer.server.port: "80"
Certificat wildcard : pourquoi c'est indispensable ici Avec un sous-domaine dynamique par tenant (créé à la volée quand un nouveau client s'inscrit), demander un certificat Let's Encrypt par sous-domaine serait ingérable (limite de taux, latence à chaque création de tenant). Un certificat wildcard (*.monapp.com) couvre tous les sous-domaines existants et futurs en une seule fois — Traefik le renouvelle automatiquement via le challenge DNS-01 (qui nécessite un accès API chez le registrar/fournisseur DNS, contrairement au challenge HTTP-01 qui ne fonctionne pas pour du wildcard).

10.3 — Déployer sans downtime : le vrai défi

Un déploiement naïf (docker compose down puis up) provoque une coupure de service pendant tout le temps du remplacement. Coolify — comme la plupart des plateformes modernes — utilise une stratégie proche du rolling update : démarrer le(s) nouveau(x) conteneur(s), attendre qu'il(s) soi(en)t healthy, basculer le trafic Traefik, puis seulement arrêter l'ancien conteneur.

Étape du rolling updateDétail
1Démarrage du nouveau conteneur en parallèle de l'ancien (les deux tournent temporairement)
2Attente que le HEALTHCHECK du nouveau conteneur passe à healthy (chapitre 8)
3Traefik détecte le nouveau conteneur sain sur le réseau partagé et commence à lui envoyer du trafic
4Bascule complète du trafic, arrêt propre de l'ancien conteneur (délai de grâce pour terminer les requêtes en cours)
Prérequis pour que ça fonctionne vraiment sans coupure
  • Un HEALTHCHECK fiable et représentatif de la disponibilité réelle du service (chapitre 8)
  • Les migrations de base de données doivent être rétro-compatibles pendant la fenêtre où ancienne et nouvelle version tournent en même temps (éviter par exemple de supprimer une colonne encore utilisée par l'ancienne version)
  • Les workers de queue (queue:work) doivent gérer proprement l'arrêt (--max-time, écoute des signaux SIGTERM) pour ne pas perdre de jobs en cours
  • Les sessions ne doivent pas être stockées dans la mémoire locale du conteneur (préférer Redis) pour survivre au remplacement du conteneur applicatif

10.4 — Gérer les rebuilds : cache et migrations

bash
# Étape typique d'un script de déploiement (souvent exécutée dans un entrypoint,
# ou une "commande post-déploiement" Coolify, PAS au moment du build de l'image)
php artisan migrate --force
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan queue:restart
queue:restart, pas un simple redémarrage de conteneur php artisan queue:restart demande aux workers de queue de terminer proprement leur job en cours puis de s'arrêter, avant que le superviseur de processus (supervisord, dans une configuration comme celle utilisée pour cette stack) ne les relance avec le nouveau code. C'est plus sûr qu'un kill -9 qui risquerait de perdre un job en plein traitement.
🧩 Mise en situation — "Conflit de port au déploiement d'un service additionnel"
Contexte

Un développeur ajoute un service mailpit (outil de test d'emails) au compose avec ports: ["8025:8025"]. Le déploiement échoue avec une erreur de conflit de port.

  2. Mieux : ne pas publier ce service sur l'hôte du tout, et y accéder via un routeur Traefik dédié sur un sous-domaine (mailpit.monapp.com), en cohérence avec la bonne pratique du chapitre 4 ("seul Traefik publie des ports")

11.4 — Étape 3 : le script d'entrypoint

Comme discuté au chapitre 9, on préfère générer les caches Laravel (config/route/view) au démarrage du conteneur plutôt qu'au build de l'image, pour garantir qu'ils reflètent toujours les variables d'environnement réellement disponibles au runtime.

docker/entrypoint.shbash
#!/bin/sh
set -e

echo "Attente de la disponibilité de la base de données..."
until php artisan db:show > /dev/null 2>&1; do
  echo "  ...MariaDB pas encore prête, nouvelle tentative dans 2s"
  sleep 2
done

echo "Application des migrations (sans interaction)..."
php artisan migrate --force

echo "Régénération des caches applicatifs..."
php artisan config:clear
php artisan config:cache
php artisan route:cache
php artisan view:cache

echo "Démarrage du process principal : $@"
exec "$@"

11.6 — Étape 5 : checklist de mise en production

  • Le réseau externe traefik-public existe déjà et est partagé avec le conteneur Traefik (créé une fois par Coolify sur le VPS)
  • Le DNS wildcard *.monapp.com pointe vers l'IP du VPS, et le certificat SSL wildcard est configuré via le challenge DNS-01 chez le fournisseur DNS
  • Les secrets (mots de passe DB, clé d'application Laravel APP_KEY) sont gérés via les variables d'environnement Coolify, jamais commités dans le Dockerfile ni dans le dépôt Git
  • Chaque service dispose d'un healthcheck pertinent et d'une politique restart: unless-stopped
  • Les volumes mariadb-data, redis-data et tenant-storage sont couverts par une stratégie de backup automatisée et testée (chapitre 5)
  • Le scan de vulnérabilités (Trivy) est intégré au pipeline CI, avant le déploiement
  • Le déploiement suit une logique de rolling update sans downtime, avec migrations rétro-compatibles (chapitre 10)
  • Le monitoring (métriques + logs centralisés) couvre l'ensemble des conteneurs, avec des alertes sur la consommation mémoire/CPU par tenant
